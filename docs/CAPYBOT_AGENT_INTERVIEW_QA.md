# Capybot Apply Agent 开发面试问答

更新时间：2026-07-30

以下回答按照当前项目代码编写，尽量控制在面试时 30～60 秒可以说完。回答时不用逐字背诵，记住每题的结论、一个实现点和一个结果即可。

## 一、项目价值

### 1. 请你介绍一下 Capybot Apply，它解决了什么问题？

Capybot Apply 是一个本地运行的求职进度 Agent。它解决的问题是：联系很多 HR 以后，我经常记不住每个岗位聊到哪一步，也不知道现在应该先回复谁。

系统会只读导入 BOSS 聊天和岗位卡，把聊天整理成一个个岗位机会，再生成当前阶段、下一步行动、任务、回复草稿、风险和岗位契合度。复杂情况会由 LLM 动态调用 Memory、Skill 和 MCP，最后经过证据校验再写入数据库。系统只给建议，不会自动发送消息。

### 2. 从点击导入到前端出现结果，完整流程是什么？

用户点击导入后，FastAPI 先创建后台任务，Celery Worker 通过 CDP 连接专用 Chrome，读取近 30 天聊天和岗位卡。原始数据标准化后写入 PostgreSQL，并通过 `message_id` 或内容指纹识别新增消息。

DecisionRouter 先跳过无变化和平台自动消息。有真实 HR 变化的机会才进入 OpenAI Agents SDK 驱动的机会 Agent。Agent 可以按需读取 Memory、加载 Skill 或调用 MCP。结果经过 CommitGate 校验证据和安全边界后写库，最后通过 Redis 和 WebSocket 通知前端局部刷新。

### 3. 用户可以体验到哪些功能？

用户可以登录 BOSS、导入聊天、查看每个岗位的阶段和下一步，还能管理任务、回复草稿和风险。上传 PDF 简历后，系统会生成候选人画像，计算岗位契合度和机会优先级。

机会详情可以展开原始证据，Agent 页面还能看到模型调用了什么工具、拿到了什么信息，以及结果有没有通过校验。所以它不只是聊天总结，而是一个可追溯的求职行动台。

### 4. 哪一步必须使用 Agent，为什么不能全部使用规则？

确定性的事情我都用代码做，比如去重、增量检测、权限和提交校验。真正需要 Agent 的是招聘语义理解和工具选择。

例如 HR 说“岗位会接触一些大模型，具体面试聊”，规则很难判断岗位是否真的匹配。Agent 可以先发现信息不足，再决定读取岗位、加载尽调 Skill 或调用 BOSS MCP，拿到新信息后重新判断。这种根据 Observation 改变下一步的过程，不适合写成固定 Workflow。

## 二、数据获取与建模

### 5. Chrome CDP、Cookie 和独立 Profile 分别有什么作用？

Capybot 会启动一台专用 Chrome。用户扫码后，Cookie 和缓存由 Chrome 保存在独立 Profile 中，因此登录态正常时，下次可以直接复用。

CDP 是程序控制这台 Chrome 的通道，用来检查登录状态、进入聊天页和执行只读请求。系统不会读取用户日常 Chrome 的 Profile，也不要求手动粘贴 Cookie。

### 6. BOSS 没有公开 API，你是怎么获取聊天的？这算爬虫吗？

项目没有使用 BOSS 官方开放 API，而是在用户主动登录网页后，复用浏览器会话，读取网页自己使用的会话、历史消息和岗位接口。

从技术上看，它属于浏览器自动化和只读数据采集。但项目重点不是大规模爬取，而是同步用户自己的求职数据并进行增量决策。它低频、本机运行，而且没有发送、打招呼和自动投递能力。

### 7. BOSS 的各种 ID 是怎么来的？

`boss_uid`、会话 ID、岗位 ID 和 `message_id` 都来自 BOSS 页面或内部接口的原始响应，不是系统编造的。

平台 ID 用来关联联系人、聊天、岗位和消息；Capybot 另外生成 Opportunity ID、Import Run ID 和 Agent Run ID，用来管理本地业务关系和 Trace。

### 8. 消息如何去重？

正常消息优先使用 BOSS 的 `message_id` 去重。如果 ID 缺失或异常，就根据发送方、发送时间、消息类型、正文或附件生成内容指纹。

Importer 和数据库唯一约束会共同保证幂等，所以重复导入不会重复写消息，也不会重复触发 Agent。

### 9. 首次导入和后续导入有什么区别？

首次导入要建立 L1 原始数据和 Opportunity，并为有真实互动的机会生成初始分析。只有我方自荐、HR 没回复的冷机会，可以直接标成已发现并等待，不需要调用 LLM。

后续导入只处理新增消息。没有新增内容的机会完全跳过，这样不会重复消耗模型，也不会因为模型随机性覆盖原来正确的状态。

### 10. 为什么需要 Opportunity，而不是直接管理聊天框？

用户真正关心的是岗位机会，而不是聊天窗口。一个 HR 可能在同一个会话里推荐多个岗位，如果直接把会话当机会，阶段和评分就会混在一起。

Opportunity 把岗位、联系人、聊天、阶段、任务、风险和评分聚合起来。Agent 每次只分析一个机会，上下文更小，业务含义也更清楚。

## 三、Agent Runtime

### 11. 第一轮 LLM 输入包含什么？

第一轮主要包含 System Policy、当前机会的精简状态，以及本次新增消息 Delta。不会直接放入完整历史、整份简历和所有岗位资料。

模型还会通过 OpenAI 的 `tools` 参数看到当前可用工具的名称、描述和参数 Schema。如果信息不足，再主动读取 Memory、Profile、Skill 或 MCP。

### 12. 为什么不把所有上下文一次性塞给 LLM？

全部塞进去会增加 Token 和延迟，旧消息也容易干扰模型关注本次变化，而且结果出错后很难知道它依据了什么。

Capybot 先提供最小上下文，需要什么再通过工具补充。真实回放中，相比全量 One-shot，LLM 调用减少 60%，Token 减少 66.05%，模型处理时间减少 63.37%。

### 13. 举一个完整 Agent Loop 的例子。

比如 HR 说岗位会涉及大模型，但没有说明具体职责。模型先加载岗位尽调 Skill，得到“先检查本地岗位，再补关键事实”的方法。

它读取 `job_read` 后发现信息不完整，于是调用 `boss_fetch_job_detail`。MCP 返回完整岗位职责后，模型重新判断岗位是否偏运营或实施，再生成风险和向 HR 追问的问题。最终结果引用新岗位快照，通过 CommitGate 后才写库。

### 14. 为什么它是 Agent，而不是固定 Workflow？

固定 Workflow 会提前规定先调用 A、再调用 B。Capybot 只固定安全规则和输出格式，没有固定工具路径。

证据足够时模型可以直接结束；缺历史时读 Memory；需要回答项目经历时加载沟通 Skill；岗位信息不足时调用 MCP。工具结果会进入下一轮，模型再决定继续还是停止，所以不同机会的路径和轮数并不一样。

### 15. 为什么使用受限 Agent，而不是完全自由 Agent？

因为它处理真实账号、简历和聊天，错误操作的风险很高。机会 Agent 只允许 Apply 白名单工具，没有 Shell、任意文件、自由搜索和 BOSS 写操作。

模型也不能直接写数据库，只能提出结构化决策，再由 CommitGate 校验后提交。我希望模型在语义判断上灵活，但在权限、证据和副作用上必须可控。

### 16. DecisionRouter 和机会 Agent 如何配合？

DecisionRouter 只处理代码能够确定的边界，比如没有新增消息、只有平台卡片，或者首次导入只有候选人单向自荐。这些情况可以零 LLM 跳过。

一旦出现真实 HR 消息、面试、风险或语义不确定性，就交给机会 Agent。这样既保留 Agent 处理复杂语义的价值，也不会为了展示 Agent 而让所有消息都调用模型。

## 四、Tool 与 MCP

### 17. 当前有哪些本地 Tool？

有三个：`memory_read` 读取隐藏的历史消息或事件，`job_read` 读取本地岗位证据，`profile_read` 读取脱敏候选人画像。

它们读取的是进程内和 PostgreSQL 已有数据，所以是本地 Typed Tool，不需要包装成 MCP。没有对应数据时，Toolbox 也不会把工具暴露给模型。

### 18. 当前有哪些外部 MCP？

有两个 MCP Server、三个 MCP Tool。BOSS Server 提供 `boss_refresh_opportunity` 和 `boss_fetch_job_detail`，分别补查当前机会和完整岗位详情；Company Intel Server 提供 `research_company`，用于核验公司业务和招聘关系。

这些工具都会绑定当前 Opportunity，模型不能更换账号、岗位和公司，也不能传自由搜索词。

### 19. 本地 Tool 和 MCP 有什么区别？

本地 Tool 读取系统已经拥有的数据，调用快，也没有独立外部权限。MCP 连接进程外能力，比如 BOSS 页面和公司公开来源，需要处理超时、权限和协议变化。

我的原则是按能力边界划分，而不是为了增加 MCP 数量。像 `memory_read` 做成 MCP 只会增加复杂度，没有实际收益。

### 20. 如何证明 MCP 调用真的有价值？

外部 MCP 会返回新的 `boss_job_snapshot` 或 `web_source`，不是重复数据库摘要。Trace 会记录新增证据数量，以及这些证据最后有没有被决策采用。

如果工具返回了新证据，但最终结果没有引用，系统会要求模型修复，仍未使用就拒绝提交。真实验证中，岗位工具曾读取 1,622 字岗位详情，公司工具也拿到了多条公开招聘来源。

### 21. MCP 调用失败怎么办？

普通工具的超时、空结果和错误会形成结构化 Observation，Agent 可以基于本地 L1/L2/L3 继续分析；用户明确要求的必需补查失败时则 fail closed，并保留旧状态。

如果证据仍然不足，就返回 `needs_review`，并保留旧状态。工具失败本身不会被当作岗位风险，BOSS 超出 30 天或岗位下架也不会删除本地历史。

## 五、Skill 与 Memory

### 22. Skill、Prompt 和 MCP 有什么区别？当前有哪些 Skill？

Skill 可以理解为按场景加载的专业 Prompt，但它还包含处理步骤、工具策略、停止条件和完成标准。MCP 则负责真正获取外部事实。

当前有三个 Skill：有依据的候选人沟通、岗位机会尽调和针对性面试准备。普通阶段判断、机会排序和岗位评分都没有硬包装成 Skill。

### 23. Skill 如何实现渐进式披露？

第一轮模型只看到三个 Skill 的名称和用途，不会看到完整正文。模型根据当前消息选择是否调用，调用后下一轮才会加入对应 `SKILL.md`。

Skill 还会在白名单内解锁需要的证据工具。例如岗位尽调可以开放岗位详情和公司查询，但不能绕过 `allow_external=false`，也不能访问其他机会。

### 24. L1/L2/L3 三层记忆分别是什么？

L1 保存原始聊天、岗位卡和外部来源，是证据事实层；L2 保存材料、面试、等待反馈和风险等结构化事件；L3 保存机会和联系人的长期摘要。

首次导入先写 L1，再由 Agent 建立 L2/L3。后续导入只根据新增消息更新。模型平时优先使用摘要，需要核对历史细节时才通过 `memory_read` 回查。

## 六、输出、可靠性与评测

### 25. Agent 最终输出什么？岗位评分是怎么来的？

机会 Agent 最终只输出状态、阶段、摘要、下一步、变化、建议和置信度。建议只包含任务、草稿和风险，每个关键结论都要引用聊天、岗位或简历证据。

岗位契合度由独立 JobFitEvaluator 计算。模型判断六个证据维度，代码按固定权重聚合，并检查城市、周期、薪资和收费风险。机会优先级再结合 HR 互动、阶段、活跃度和风险。

### 26. 如何证明 Agent 比单次 LLM 更有效？

我用本人 41 个 BOSS 会话、267 条消息构造了 57 个时间增量轮次，并和同模型全量 One-shot 做 A/B。增量 Agent 的 LLM 调用减少 60%，Token 减少 66.05%，模型处理时间减少 63.37%。

在 LLM 双标注裁决参考集上，增量 Agent 的最终阶段和行动联合一致率是 100%，One-shot 是 62.5%。这个结果不是生产准确率，我会主动说明样本只有个人求职规模，参考标签也不是人工 Gold Set。

系统还通过 Evidence Ledger、CommitGate 和 Tool Trace 验证可靠性。Memory Tool 优化后，工具执行从 21 次降到 11 次，空结果从 10 次降到 0，Token 又减少 6.66%，最终质量没有回退。
